# Agent Note: 本地 MCP 接口驱动迁移与回迁

Status: implemented

## Problem

Issue #3 要求提供 MCP 服务供 AI 读取和调用，能够创建和执行迁移与回迁，效果与 App 一致，结果必须能在 App 中操作。AppPorts 现有迁移入口都在 SwiftUI 视图状态里：外部进程既读不到应用列表与迁移日志，也无法把迁移交给任务中心，所以只做一条 CLI 或直接复制文件都会产生第二套迁移语义。

## Decision

App 内新增一条仅监听 `127.0.0.1` 的 Streamable HTTP MCP 端点，默认关闭、需在设置中显式开启，并为每个安装生成 Bearer 令牌；同时校验 `Origin`，只接受回环来源。一次 POST 承载一条 JSON-RPC 消息，响应固定为 `application/json`，不开启 SSE，也不向客户端发请求。协议版本按 `2025-06-18`、`2025-03-26`、`2024-11-05` 协商。

工具面按三类能力展开，共十三个：

- 应用：`appports_status`、`appports_list_apps`、`appports_list_transfers`、`appports_migrate_app`、`appports_restore_app`。
- 路径：`appports_list_paths`（应用 `~/Library` 数据目录、工具目录、自定义目录，含状态与迁移方式，只读）、`appports_migrate_path`、`appports_restore_path`。
- 数据：`appports_list_data_migrations`（挂载记录、托管链接、迁移日志、待清理事项与微信账号状态，只读）、`appports_migrate_wechat_account`、`appports_restore_wechat_account`。
- 任务：`appports_task`、`appports_cancel_task` 覆盖全部三类写操作；暂停、取消、重试与手动操作完全一致。

路径与数据工具的实现放在 `MCPToolService+Data.swift`，动作本身不重写迁移逻辑，而是复用界面用到的同一批服务：符号链接迁移走 `DataDirMover`（`migrateAndComplete` / `restoreAndComplete` / `createLink`），容器目录走 `ContainerVolumeMigrator`（挂载迁移与还原），微信账号走 `WeChatAccountMigrationService`（拆分/整体迁移与还原）；应用数据目录迁移前仍调用 `AppDataMigrationPreparation.refresh`，与 `DataDirsView` 相同地重扫、校验磁盘权限与目录身份。所有写操作提交到 `MigrationTaskCenter`，因此共享操作锁、journals、挂载记录、清理记录与任务中心展示，完成后发 `appports_recordsDidChange` 让主界面重扫。

路径与数据的预检照抄界面判定，不另立规则：目录必须来自扫描结果或已配置的自定义目录（否则 `PATH_NOT_FOUND` / `APP_REQUIRED` / `PATH_NOT_A_DATA_DIRECTORY`）；应用数据目录与微信账号要求 App 位于「应用程序」且已获得完全磁盘访问（`INSTALLATION_LOCATION`、`ACCESS_DENIED`，与界面一致；工具目录和自定义目录在界面中不做这两项检查，工具同样不检查）；关联应用运行中、有未完成迁移记录、前台操作进行中分别返回 `RUNNING`、`PENDING_TRANSFER`、`BUSY`；容器目录在经典模式下才允许符号链接，否则明确返回 `MOUNT_REQUIRED`；挂载迁移复用 `MountMigrationPreflight`，把非 APFS、加密卷、空间不足、目标不可用映射成对应错误码；微信账号拆分迁移要求用户已在设置中开启（`WECHAT_DISABLED`），状态冲突与“先还原再切换”分别返回 `WECHAT_CONFLICT`、`RESTORE_FIRST`。同一路径的微信账号调用路径工具会被重定向到账号工具（`WECHAT_ACCOUNT`），避免用符号链接处理容器数据。

写操作不自行复制文件，而是向 `MigrationTaskCenter` 提交任务，与 UI 共用操作锁、journals、签名/搜索/Dock 收尾和任务中心展示；任务完成后按与 UI 相同的方式写入 `AppListTransfer` 与 `AppSearchRecordStore`，再由记录变化通知驱动主界面重扫。因此 AI 发起的迁移在 App 里可见、可暂停、可取消、可在失败后重试，退出 App 后任务与记录仍在。

预检与 UI 同源：新增 `AppMigrationPolicy` 统一“不可迁移”的原因，`ContentView.migrationSkipReason` 改为委派它；自更新应用（uchg 保护）必须带 `lock_external=true` 才执行；目标卷与应用同卷、目标已存在同名应用、存在未完成迁移记录、前台操作进行中，一律拒绝并给出下一步提示。回迁接受外部路径或本地入口，默认还原到 `localDestinationForRestore` 计算出的原入口位置，可用 `local_destination` 覆盖；本地存在同名真实应用时拒绝。

设置页新增“AI 接入（MCP）”区：开关、endpoint、掩码令牌、复制客户端配置、重新生成令牌。端点随 App 启动按设置恢复，App 退出即停止；XCTest 宿主不启动。

## Wire and security details

- 方法：`initialize`、`ping`、`tools/list`、`tools/call`，通知按 202 应答；未知方法 `-32601`，参数/未知工具 `-32602`，解析失败 `-32600`/`-32700`；工具内的业务失败以 `isError: true` 的文本结果返回，会话继续。
- 请求体上限 4 MB、请求头上限 32 KB；每个连接只处理一条请求，`Connection: close`。
- 令牌用 `SecRandomCopyBytes` 生成并保存在应用自己的偏好域，比较用常量时间；DNS rebinding 由 `Origin` 白名单挡住，非回环 `Origin` 返回 403，缺令牌 401。
- 工具执行留在主 actor；`MCPToolService.Environment` 把扫描、迁移/回迁步骤、卷判断、策略和任务中心全部做成注入点，测试不触碰真实应用与外置盘。

## Alternatives considered

- 独立 CLI / 独立进程跑迁移：AI 客户端可直接用 stdio 启动，App 不必常驻。但迁移必须与运行中的 App 共用操作锁与任务中心；两个进程写同一 journals 会绕过界面的忙碌状态，任务也不会出现在任务中心。放弃。
- App 二进制加 `--mcp` stdio 模式：没有 HTTP 面，最省事。但 App 是 GUI 进程，同时只能有一个实例持有迁移状态；另起 headless 进程要重做写入资格与界面刷新，任务同样进不了任务中心。放弃。
- MCP 直接调用 `AppMigrationService` 复制：代码最短。但会绕过任务中心、并发上限、暂停/取消与界面记录，与“和 App 执行功能一致”冲突。改为在任务内部执行。
- 允许 MCP 覆盖外置盘同名应用：省一次人工确认。但版本比较、降级与更新保护都需要人判断，v1 明确拒绝并指向 App 处理。
- 端点常开、只靠令牌：少一个开关。但同用户进程都能读偏好域里的令牌，误用面更大；默认关闭更符合仓库现有的显式确认风格。

## Consequences

端点只在 App 运行时存在，AI 不能在 App 退出后继续迁移；这换来的是任务、锁与记录始终由同一个进程拥有。

数据迁移仍有几处刻意不开放：容器目录与组容器仍然只能用挂载迁移，MCP 不会替用户绕过沙箱检查去建符号链接；加密卷的密码、APFS 失败后的恢复选择、目标盘选择等需要人判断的步骤仍回到 App 内完成，工具只返回对应错误码；微信账号只提供拆分模式的还原（`restore_wechat_account` 对整体迁移返回 `NOT_SPLIT_MIGRATED`，需在 App 中用原有的整体还原流程）；账号拆分迁移本身仍要求用户先在设置中开启。这些限制与界面完全一致，是“复用同一条执行路径”的必然结果，而不是另做判断。MCP 不新增任何文件系统权限，写操作仍走服务层校验。今后任何新的迁移入口都应复用 `AppMigrationPolicy` 与任务中心，否则会再次出现两套行为。令牌保存在偏好域，同用户进程仍可读取；端点默认关闭、仅回环、带 Origin 校验，是这一取舍下的边界。
